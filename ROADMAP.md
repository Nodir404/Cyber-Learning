Этот файл сохраняет решения о приоритетах и следующих шагах. При продолжении
работы сначала сверяем план с актуальным кодом, тестами и состоянием GitHub.
Идеи ниже считаются планами, пока их реализация и проверки не подтверждены.

## Основное решение

- **SSH Log Analyzer — главный проект.** Основное время разработки направляем
  на него. Работаем небольшими изменениями через PR с понятной целью и проверкой.
- **Конспекты Nmap сохраняем** в `notes/nmap/`. Дополняем их собственными

- **Burp Authentication Lab сохраняем** как небольшую учебную демонстрацию.
  Возвращаемся к развитию по мере изучения веб-безопасности.
- Новый инструмент начинаем после завершённого этапа основного проекта.
  Количество репозиториев само по себе не является целью.

## Для чего нужен SSH Log Analyzer

OpenSSH записывает события входа в журналы. Анализатор помогает превратить
поддерживаемые записи в сводку: сколько входов прошло успешно, сколько завершилось
ошибкой, с каких IP приходили попытки и какие IP превысили выбранный порог ошибок
за промежуток времени. CSV позволяет изучить результат в другой программе.

Например, в учебном журнале у одного IP может быть пять неудачных попыток за
пять минут. Анализатор покажет соответствующий интервал для проверки. Причиной
могут быть подбор пароля, неверно настроенная программа или ошибки пользователя.
Предупреждение само по себе не доказывает атаку.

Текущая версия читает локальный файл. Она не блокирует IP, не наблюдает за
сервером непрерывно и не устанавливает личность человека за адресом.

Проект развивает Python, обработку логов Linux, работу со временем, тестирование,
объяснение алгоритмов и подготовку отчётов. Это практическая основа для дальнейшей
работы с обнаружением событий, SOC и расследованием инцидентов. Практику
пентестинга, сетей и веб-безопасности продолжаем отдельными упражнениями.

## Что уже реализовано

- Поддерживаемые сообщения OpenSSH об успешных и неудачных входах.
- Счётчики по IP, проверка IPv4/IPv6 и нормализация IPv6.
- Учёт пропущенных строк и экспорт сводки в CSV.
- Обнаружение всплесков неудачных попыток в скользящем временном окне.
- Тесты, синтетические примеры логов и инструкции запуска.

Текущие ограничения описаны в
[README анализатора](projects/ssh-log-analyzer/README.md). В частности,
обнаружение всплесков требует явно указать год и поддерживает ограниченный
формат даты; JSON-отчёт ещё не реализован.

Небольшие изменения вроде процента неудачных попыток можно включать отдельными
задачами, если понятна их польза и определено поведение для пустого журнала.
Графики и визуальный интерфейс добавляем после проверки числовых результатов.

Этап 0 подготовлен в изменении с этим планом. Фактическое прохождение проверок
смотрим в GitHub Actions; наличие файла workflow не означает успешный запуск.
Этапы 1–5 остаются предстоящей работой.

## Сбалансированное портфолио: следующие работы

| Очерёдность | Работа | Простыми словами | Что демонстрирует |
| --- | --- | --- | --- |
| Сейчас | SSH Log Analyzer | Найти заслуживающие проверки события в журнале входов | Python, Linux, defensive security, время и тесты |
| После завершённого этапа анализатора | Nmap Report Inspector — рабочее название идеи | Прочитать сохранённый XML-отчёт Nmap, показать хосты, порты и сервисы; затем сравнить два совместимых отчёта | Понимание сетей, обработка структурированных данных и объяснение изменений |
| По мере изучения веб-безопасности | Развитие Burp Authentication Lab | Воспроизвести ошибку прав доступа, показать исправление и проверить его тестами | HTTP, cookies, серверные сессии и контроль доступа |

Nmap Report Inspector пока отсутствует. Его первый этап — небольшой локальный
анализатор готового отчёта. При сравнении учитываем различия параметров и полноты
сканирования; отсутствие порта в отчёте не всегда означает, что порт закрыт.
Открытый порт сам по себе не доказывает уязвимость. Первые примеры и результаты
связываем с соответствующими конспектами.

Визуальную карту собственных конспектов или результатов можно рассмотреть позже
как отдельную идею. Решение о её формате принимаем при начале этой работы.

Burp-лаборатория остаётся учебной. При возвращении сначала проверяем обработку
cookies, границы прав доступа и тесты для нескольких сценариев. Полный вход,
выход и срок жизни сессий требуют отдельных задач и не считаются уже готовыми.

## Как показывать свою работу

- В начале README объяснять задачу инструмента и давать воспроизводимый пример.
- Публиковать ожидаемый результат, тесты и ограничения вместе с кодом.
- Для лаборатории объяснять: ошибка → воспроизведение → причина → исправление → проверка.
- Описывать личный вклад и помощь ИИ честно; уметь объяснить ключевые решения.
- Делать небольшие PR с причиной изменения и результатом проверки.
- После выделения анализатора закрепить его репозиторий в профиле GitHub.
